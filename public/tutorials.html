What HydraFusion is

For each request, it plans the steps and picks a model for each one.

HydraFusion is a GitHub Copilot model, in research preview, that plans each request and picks a model for each step. This app runs three prompts against a web page with accessibility problems built in, and shows which pattern HydraFusion picked, each step as it runs, and what it cost.

A request goes through a router that scores reasoning, code, debugging and tool use. It chooses a pattern and a model for each step. The dashboard's routing panel fills in with the real route when you run or replay a demo.

  • A research preview, listed after Auto in the model picker
  • Two tiers, Default and Max, each with its own routing policy
  • Each step can use a different model and reasoning effort
  • If routing fails, it carries on with a fallback model

Where to find it

In VS Code, pick HydraFusion in the model picker, then choose Default or Max at the right of its row. It routes the first eligible turn, so open a new chat when you want a fresh route.

This app uses the same tiers through the Copilot SDK: hydrafusion for Default and hydrafusion-max for Max, with a new session for every run.

Using the demos

Each demo starts a new session with the tier already set, then sends the prompt, as if you opened a new chat. Each prompt tends to get the pattern on its card, but the router decides. Live runs spend AIU from the server's Copilot account; replays don't.

While a live run continues, you can replay a recording and return to it. You can also visit these tutorials and use Back to demos to resume your own live run in the same tab.

Three patterns

The router picks one of these for each request. You can't pick it directly.

Single
One solver does the whole job.
Critique
A solver drafts a result, a critic reviews it in read-only history, and the original solver revises it if needed.
Cascade
A solver produces an answer, a judge scores it, and a stronger model repairs it only if it fails.

In the dashboard's pattern progress view, dashed steps only run when needed. The pattern of the run you're watching is highlighted.

Critique or Cascade

Both add a second opinion. They use it differently.

QuestionCritiqueCascade
Who reviewsA criticA judge
What the review returnsNotes on the draftA score: pass or fail
If the answer falls shortThe same model revises itA stronger model repairs it

A Critique fix stays with the same model. A Cascade fix brings in a stronger one, so it can cost more.

Behind the scenes

Reviews

  • Run in a separate, read-only history
  • Start from the answer and a summary
  • Can't change your files
  • Can miss checks that were never run

In Cascade

  • A rejected answer is held back
  • You only see the repaired answer
  • File edits from the first try stay
  • The repair can reuse or redo them

Reviews never enter your chat history, so they don't add to the size of later requests.

How to tell which one you got

Chat shows the workflow it picked, then each pass as it runs.

PatternChat saysPasses

Revision and Fix-up only show up when the review asks for changes. Try the same prompt on Default and Max, each in a new chat, and compare.

How cost is counted

Premium requests (legacy)

  • Counted per prompt, not per token
  • Each model has a multiplier
  • Some models count 1, others 15
  • Extra steps can add to it

AIU (AI Units, from June 1, 2026)

  • Counts every token, in and out
  • Each model has its own prices
  • Logs record it as nano-AIU
  • A billion nano-AIU make one AIU

The two don't always agree. A model can count as 1 premium request and still cost a lot per token.

How tokens are priced

Price per token, compared with new input, for the same model. The dashboard's token usage panel shows the run you're watching, from the SDK's billing details for each call.

Token typePrice vs new input
Read from cache0.05× to 0.1×
New input1×
Written to cache1.25×
Output5×

Base prices also vary between models. The gap can be 100 times per token.

Where it saves, where it costs more

Saves

  • Easy requests can go to a cheap model
  • Reviews skip the full chat history
  • Extra steps only run when needed
  • Repeated context is read from cache

Costs more

  • You pay for a rejected answer too
  • It may pick an expensive model
  • Long chats cost more per request

Your chat history goes with every request, so start a new chat for each test.

Testing a page for accessibility

  1. Open the page in VS Code's browser
  2. Share it with chat
  3. Pick HydraFusion in the model picker
  4. Send a prompt like this one
quickly test this page with the browser tools

It reads the page, runs Playwright checks and can press keys to test the keyboard. No terminal needed.

To try it in VS Code, copy the URL of the demo page into its browser. Live runs in this app share the same page with the session and give it the browser tools through Playwright MCP.

What a snippet can check

Each row in the interactive checks is one snippet in checks/, run on the demo page. Each one is the body of an async function with page in scope, so you can paste it into Run Playwright Code as it is. Run the checks on the main page to see measured results and open each snippet.

Use it as a first pass

It can check

  • Contrast ratios
  • Missing alt text and labels
  • Heading order and landmarks
  • Page language
  • Basic keyboard use

Then

  • Run axe-core
  • Run Accessibility Insights
  • Keep the CI checks on pull requests
  • Keyboard and screen reader testing
  • Check that alt text makes sense

Ask for measured values and screenshots, so you can check its work.

HydraFusion is a research preview. Models, prices and routing change over time, so your runs may not match the reference runs.
